# Bug: Internal Container S3 Endpoint Leaked in Client Presigned Upload URLs

- **Bug ID**: BUG-OPS-003
- **Milestone**: Operations & Production Deployment
- **Severity**: Critical (P0 - Client Upload Failure)
- **Target Files**:
  - `docker-compose.prod.yml` (line 54)
  - `server/src/services/storage.service.ts` (lines 56–72, 126–127)
  - `nginx.prod.conf`
- **Status**: Identified

---

## 1. Description

In [`docker-compose.prod.yml`](file:///home/hrutav-modha/Documents/smex-store/docker-compose.prod.yml#L54), the backend server environment defines:
```yaml
S3_ENDPOINT: http://minio:9000
```

In [`server/src/services/storage.service.ts`](file:///home/hrutav-modha/Documents/smex-store/server/src/services/storage.service.ts):
```typescript
this.s3Client = new S3Client({
  endpoint: this.endpoint, // http://minio:9000
  ...
  forcePathStyle: true,
});
...
export async function generatePresignedUpload(...) {
  ...
  const uploadUrl = await getSignedUrl(this.s3Client, command, { expiresIn });
  return { uploadUrl, s3Key, cdnUrl, expiresIn };
}
```

When an authenticated user requests a presigned upload URL via `POST /api/v1/marketplace/uploads/presigned-url`, `@aws-sdk/s3-request-presigner` constructs the signed PUT URL based on the `S3Client`'s configured endpoint:

```
http://minio:9000/smex-storage/marketplace/proofs/<userId>/<uuid>-proof.png?X-Amz-Algorithm=...
```

This internal URL is delivered directly to the client browser in the response JSON.

---

## 2. Impact

- `minio:9000` is an internal container hostname within the Docker bridge network (`smex-prod-network`).
- When the client's browser (Chrome, Safari, mobile devices) executes `fetch(uploadUrl, { method: 'PUT', body: file })`, DNS resolution fails with:
  ```
  net::ERR_NAME_NOT_RESOLVED (minio)
  ```
- No client can ever upload listing proof screenshots in a production environment.
- Furthermore, [`nginx.prod.conf`](file:///home/hrutav-modha/Documents/smex-store/nginx.prod.conf) does not expose or proxy MinIO or `/smex-storage/` on port 80/443.

---

## 3. Reproduction Steps / Proof of Concept

1. Inspect `server/src/services/storage.service.ts` line 58:
   ```typescript
   this.endpoint = options?.endpoint || env.S3_ENDPOINT || 'http://localhost:9000';
   ```
2. Note that `uploadUrl` generated by `getSignedUrl(this.s3Client, ...)` inherits `this.endpoint`.
3. In `docker-compose.prod.yml`, `S3_ENDPOINT` is set to `http://minio:9000`.
4. Call `POST /api/v1/marketplace/uploads/presigned-url`.
5. Observe that the returned `uploadUrl` begins with `http://minio:9000/...`, which cannot be resolved or accessed outside the Docker container network.

---

## 4. Root Cause

1. The AWS S3 SDK assumes that the S3 endpoint used by the application server to interact with the bucket is also directly accessible by the end-user browser generating client PUT requests.
2. When running a self-hosted MinIO container behind Nginx, the public URL must route through Nginx (or an externally reachable domain/IP), whereas the server can communicate with MinIO internally.
3. Fastify's `StorageService` lacks separation between `INTERNAL_S3_ENDPOINT` (used by server for GetObject/HeadObject) and `PUBLIC_S3_ENDPOINT` (used for client presigned upload URLs), OR Nginx must proxy MinIO under a public path like `/smex-storage/` or `/storage/`.

---

## 5. Recommended Remediation

1. In [`server/src/config/env.ts`](file:///home/hrutav-modha/Documents/smex-store/server/src/config/env.ts), introduce an optional `S3_PUBLIC_ENDPOINT` (or derive from `CLIENT_URL` / public domain).
2. If `S3_PUBLIC_ENDPOINT` is set, instantiate a client specifically for signing presigned client URLs pointing to the public reverse proxy or external S3 domain.
3. In [`nginx.prod.conf`](file:///home/hrutav-modha/Documents/smex-store/nginx.prod.conf), add a reverse proxy block forwarding `/smex-storage/` to `http://minio:9000;`.
4. If the deployment uses Cloudflare R2 or AWS S3, set `S3_ENDPOINT` directly to the public bucket URL.
